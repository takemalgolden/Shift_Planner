単なる設計案ではなく、ディレクトリ構造、全ソースコード、設定例、依存ライブラリ、テスト、ビルド手順、導入手順、利用者向けREADMEまで出力してください。

# 1. 開発の進め方と出力ルール

- 最初に要件を整理し、採用する構成と理由を簡潔に説明してください。
- 業務上の解釈が変わる点、セキュリティに影響する点、実現できない要件は、実装前に質問してください。
- 色、内部ファイル名などの軽微な実装判断は、合理的な前提を明示して進めてください。
- 既存のソースコードや「前回作成したファイル」がある前提にしないでください。
- 全ファイルを、保存先の相対パスとファイル内容の組み合わせで出力してください。
- 「以下略」「同様に実装」「ここに処理を書く」、疑似コード、未実装のTODOで必須機能を省略しないでください。
- モジュール間の関数名、API、データ形式、DB項目名を統一してください。
- 利用者が作成する設定ファイルには、完成した設定例を付けてください。
- バイナリや第三者製ライブラリの内容は出力不要ですが、取得方法とビルド方法を示してください。
- 一度に収まらない場合は、ファイル単位で分割してください。各回答の最後に、出力済みファイルと残りのファイルを示し、「続けて」と入力すれば重複なく再開できるようにしてください。
- 実行環境がある場合は実際にファイルを作成し、テストとビルドを行ってください。
- 実行環境がない場合は、実行したように装わず、未実行の確認項目と実行コマンドを明示してください。
- 社内サーバー名、Windowsアカウントなど環境固有の値だけを差し替えれば動作する構成にしてください。

# 2. 利用環境と目的

対象は、担当者が約5人、管理者が複数いるコールセンターです。

- Windows 10/11の64ビット版PCで使用します。
- 担当者・管理者とも、複数PCから起動する可能性があります。
- 各担当者には、それぞれ専用のWindowsアカウントがあります。
- 社内LANで共有されているWindows共有フォルダーを利用できます。
- インターネット接続は日常利用に不要としてください。
- 利用者PCにPythonや開発ツールをインストールせず、配布したEXEから起動できるようにしてください。
- 必要なWindowsランタイムがある場合は、種類と導入方法を説明してください。

最重要条件：
アプリ専用のWebサーバーやバックエンドサービスを起動する方式にしないでください。
localhost、127.0.0.1への接続、HTTP/HTTPS待ち受け、ポート開放、Web用証明書の設定を必要としない構成にしてください。

既存のWindowsファイル共有サービスは利用して構いません。
管理者のアプリを閉じていても、担当者は共有フォルダーに提出できるようにしてください。

# 3. 推奨する技術構成

以下を基本候補としてください。別の技術を採用する場合は理由を説明してください。

- Python 3.12以降の対応バージョン
- Windows用デスクトップアプリ
- pywebview＋WebView2などによる専用ウィンドウ
- HTML/CSS/JavaScriptをアプリ内に同梱
- Pythonと画面の間はネイティブブリッジで通信
- HTTPサーバーを起動せずに画面を表示
- 外部CDN、外部Webフォント、外部JavaScriptに依存しない
- 業務処理と画面処理を分離
- 各PC内の作業データにSQLiteを使用
- PyInstallerなどでEXEを作成

認証・暗号化には、実績のあるライブラリとWindowsの機能を使ってください。独自の暗号方式を作らないでください。

# 4. 共有フォルダーとデータ管理

共有フォルダー上のSQLiteを、複数PCがデータベースとして直接開いて更新する方式は避けてください。

実現したい動作：

- 管理者用の正式な業務データを共有フォルダーに保存する。
- 処理時は必要なデータをPC内へコピーして使用する。
- 更新時は排他制御を行い、最新データを確認してから保存する。
- 保存途中の切断で、正常なファイルが中途半端な内容に置き換わらないようにする。
- 正式データと提出の受領記録の整合性を保つ。
- 再送・再取り込みで同じ希望や連絡事項が二重登録されないようにする。
- 古い画面からの保存で、別管理者の変更を上書きしないようにする。
- SQLiteのWAL等の付随ファイルも考慮する。
- 各担当者には、本人用に作成したデータだけを配布する。
- 担当者用データに、他人の氏名・認証情報・希望休・シフトを含めない。

共有フォルダーは、例えば次の役割に分けてください。

- 管理者専用の業務データ
- 担当者とWindowsアカウントの対応情報
- 担当者ごとの提出領域
- 担当者ごとの結果領域
- 提出データの暗号化に必要な情報
- 編集・保存の排他制御用領域

実際のディレクトリ構造と、各領域の読み取り・書き込み権限を提示してください。

# 5. 複数管理者による同時利用

- 同じ月を編集できる管理者は1人だけとする。
- 他の管理者は同じ月を閲覧できる。
- 別々の月は並行して編集できる。
- 従業員、勤務パターン、必要人数などの共通設定の編集は、月の編集とも競合しないようにする。
- 編集できるかどうかを画面上で明示する。
- 閲覧モードでは変更ボタンを無効にし、バックエンド側でも変更を拒否する。
- 終了・ログアウト・異常終了時のロック解放を考慮する。
- 時間が経ったという理由だけで、稼働中のロックを削除しない。
- 別の管理者が編集中の月に関する提出は、取り込みを保留できる。
- 保留後も、担当者ごとの提出順序を維持する。

# 6. アカウントとログイン

- 管理者・担当者とも、起動のたびに社員番号とパスワードを要求する。
- 下書き専用起動でもログインを省略できない。
- 初期管理者の登録機能を設ける。
- 担当者の新規登録申請、管理者による承認・却下・利用停止を設ける。
- 管理者による担当者の直接登録とパスワード再設定を設ける。
- パスワードは平文保存しない。
- 初期共通パスワードを埋め込まない。
- 画面上では「ログインID」ではなく「社員番号」と表記する。
- 社員番号は、先頭の0を保持できる文字列として扱う。
- 社員番号は半角英数字と「.」「_」「-」の3～32文字を基本とする。
- パスワードは8～16文字、英大文字・英小文字・数字・記号のうち3種類以上を基本とする。
- Windowsアカウントとアプリの社員番号を管理者が対応付ける。
- 同一人物がPCごとに別のローカルWindowsアカウントを使う場合、複数のSIDを同じ社員番号に対応付けられるようにする。
- 1つのSIDを複数の社員番号へ割り当てない。
- 社員番号や送信データ中のuser_idを書き換えても、他人として提出できないようにする。
- Windowsへのログイン用アカウントと共有接続用アカウントが異なる場合の設定方法を示す。
- オフライン時のパスワード変更・利用停止の反映限界を説明する。

# 7. 担当者への配布

担当者が共有フォルダーのパスを手入力する運用にはしないでください。

- 管理者が共有フォルダーのパスを設定する。
- 管理者画面から「担当者配布ZIPを作成」できる。
- ZIPにはアプリ本体、接続先設定、担当者用起動ファイル、簡単な説明書を含める。
- パスワード、個人データ、管理者用秘密鍵を配布ZIPに含めない。
- 担当者はZIPをすべて展開し、起動ファイルを開くだけで利用できる。
- 接続先設定ファイルはアプリと同じフォルダーに置く。
- 共有パスは「\\サーバー名\共有名」のようにPC間で共通に使える形式を使用する。
- 管理者PC内だけを指すローカルパスを、そのまま担当者用設定として配布しない。
- 接続先変更時の再配布手順を説明する。

# 8. 担当者の希望休・連絡事項

- 月を選んでカレンダーから複数日を選択できる。
- カレンダーは日曜始まりとする。
- 日付ごとに、有給・公休・希望休を選べる。
- 終日・午前・午後を指定できる。
- 日付ごとの備考を入力できる。
- 日付を指定しない連絡事項も提出できる。
- 希望休の備考は500文字、日付なしの連絡事項は1000文字を基本上限とする。
- 希望休は1回につき最大120日分を基本とする。
- 提出状況、管理者の取り込み結果、承認・却下、管理者コメントを確認できる。
- 「取り込み済み」と「承認済み」を明確に区別する。
- 未審査の希望について、変更・取消の手順を用意する。
- 審査済みの希望は、担当者が無断で変更できないようにする。
- 下書きの選択解除と、提出済み希望の取消を混同させない。

# 9. 詳細な勤務希望

希望休とは別に、次の勤務希望を提出できるようにしてください。

1. 日付別の勤務帯
   - 早番
   - 中番
   - 遅番
   - ショート

2. 日付別の勤務時間の範囲
   - この時刻以降に開始
   - この時刻までに終了

3. 対象月の勤務の並び順
   - 例：前日が早番なら翌日は遅番を希望
   - 例：前日が遅番なら翌日は中番を希望

並び順の定義：

- 「翌日」は次の暦日とする。
- 休みを飛ばした次の勤務日ではない。
- 両日とも勤務する場合に評価する。
- 並び順の希望だけで、休みの日を強制的に勤務日にしない。
- 月初の判定では、前月末の確定勤務も参照する。
- 補充処理で過去の日に勤務を追加するときも、前後の並び順を評価する。

日付別の勤務希望を出した日が勤務なしになった場合は、未達として確認できるようにしてください。

勤務希望は、担当者が提出し、管理者が取り込んで内容を確認・承認した後に生成へ使う方式としてください。

# 10. 備考を生成条件へ反映する機能

自由文をAIで勝手に解釈して、そのまま勤務へ反映する方式にはしないでください。

採用する方式：

- 管理者が希望休の備考や日付なし連絡事項を確認する。
- 元の文章と担当者を、条件登録フォームへコピーできる。
- 管理者が対象日、勤務帯、開始・終了時刻、勤務の並び順などを指定する。
- 管理者が条件を承認してから、シフト生成で使用する。
- 条件化した元の文章を確認できるようにする。
- 複数条件を含む文章は、複数の条件として登録できる。
- 対応していない条件を、解釈できたように扱わない。

例：
「10日は家庭の都合で18時までに退勤したい」
→ 管理者が10日の終了時刻上限を18:00として登録・承認する。

# 11. 希望の優先度と未達表示

勤務希望は、必ず守る条件ではなく、できる限り優先する条件として扱います。

- 承認済み休暇や勤務可能パターンなどの制約を守る。
- 必要人数、スキル、勤務日数との兼ね合いで希望を満たせない場合も生成できる。
- 希望を無視したまま黙って処理を完了しない。
- 管理者画面に「満たせなかった勤務希望」を一覧表示する。
- 一覧には担当者、対象日、希望条件、実際の割り当て、備考を表示する。
- 手動修正後も現在のシフトに対して再評価する。
- 矛盾した希望、希望の勤務帯が存在しない場合、勤務可能パターンと合わない場合も扱う。
- 同じ条件の二重登録によって、不自然に優先度が上がらないようにする。
- 評価方法、優先度の付け方、アルゴリズムの限界を説明する。

条件の承認・変更だけで、既存のシフトを自動的に書き換えないでください。
反映には再生成または管理者の手動調整を必要としてください。

# 13. シフト生成の業務条件

対象スキルは次の6種類とします。

- merchant・ボイス
- merchant・ノンボイス
- consumer・ボイス
- consumer・ノンボイス
- PP
- オンライン

基本の営業時間は09:20～23:00、時間の単位は10分です。

初期勤務パターンの例：

- 早番：09:20～18:20
- 中番：11:00～20:00
- 遅番：14:00～23:00
- ショート：09:20～14:20

勤務パターンは管理者が変更できます。

生成時は、以下を考慮してください。

- 必要人数
- 保有スキル
- 勤務可能パターン
- 承認済み有給・公休
- 希望休
- 詳細な勤務希望
- 週最大勤務日数
- 月最低・最大勤務日数
- 最大連続勤務日数
- 前後の月の確定勤務による週・連勤への影響
- 昼休憩・短時間休憩中の人数不足

週の区切りは日曜～土曜としてください。

複数スキルを持つ担当者を、各スキルの対応可能人数へ重複計上する方式を基本とします。この方式の意味と限界を説明してください。

月最低・最大勤務日数が未設定の場合の勤務目標は、週最大勤務日数と月の日数から算出する方式を基本とし、具体的な式を示してください。

必要人数を満たせない場合でも、不足を明示した案を作成できるようにしてください。成立しない条件を満たしたと偽って表示しないでください。

# 14. 休憩配置

以下をアプリ上の業務ルールとして実装してください。

- 7時間以上の勤務枠には、60分の昼休憩と10分休憩2回を配置する。
- それより短い勤務枠には10分休憩1回を基本とする。
- 休憩は勤務時間内に収め、勤務開始・終了の直近30分を避ける。
- 休憩同士を重複させない。
- 2回の10分休憩は、前の休憩終了から次の開始まで60分以上空ける。
- 昼休憩の開始候補は11:30～18:50の範囲とする。
- 早番の昼休憩開始は11:30、または12:00～14:00とする。
- 早番で昼休憩が11:30開始の場合は、10分休憩2回を昼休憩後に配置する。
- それ以外の早番、および中番は、昼休憩の前後に10分休憩を配置する。
- 遅番・ショートで昼休憩が必要な場合は、配置可能性を確認し、原則として前後に配置する。
- 人数不足をできる限り小さくする位置を選ぶ。
- 配置できない休憩は、未配置として管理者へ表示する。

これらを法令適合の保証として扱わないでください。矛盾や不明点があれば、実装前に確認してください。

# 15. シフトの表示・確定・出力

- 日曜始まりの月間カレンダー
- 管理者の全員表示と個人表示
- 担当者本人の確定済みシフト表示
- 早番・中番・遅番・ショートを色分け
- 日付別の勤務時間・休憩時刻の表示
- 必要人数不足、休憩未配置、勤務条件違反の表示
- 勤務希望の未達一覧

シフトの状態は、下書き→一次確認済み→確定としてください。

- 確定済みの月を変更するには再編集操作を必要とする。
- 一次確認後に関連条件を変更した場合は、再確認が必要な状態へ戻す。
- 担当者には本人の確定済みシフトだけを公開する。
- 警告がある状態で確定する場合の確認手順を設ける。

出力形式：

- 全員分のExcel
- 個人分のExcel
- 個人別ExcelをまとめたZIP
- CSV
- 業務データのバックアップ

Excelの全員分は氏名×日付の一覧、個人分は月間カレンダーと勤務明細を基本としてください。
ユーザー入力をExcelの数式として実行させないでください。

# 16. 下書き・オフライン利用・JSON

- 初回設定と本人データの取得を済ませたPCでは、共有接続が切れていてもログインし、希望入力や提出待ち保存ができる。
- 初回から完全オフラインで利用できるとは案内しない。
- 提出待ちデータは暗号化する。
- PC内の下書きはWindowsのDPAPI等で保護する。
- 接続復旧後、起動時・操作時・一定間隔で再送する。
- アプリ終了中に送信されるとは案内しない。
- 別PCへ下書きや未送信データが自動移動するとは案内しない。
- JSONの保存・読み込み、管理者へのファイル受け渡しを提供する。
- JSONの提出者と取り込み先の一致を確認する。
- ファイルサイズ、件数、日付、文字数、型を検証する。
- JSON形式にはバージョンを持たせ、具体的なサンプルを示す。
- 新しい勤務希望がJSONに対応するかを明示し、保存・読み込みで条件を黙って落とさない。

# 17. UI

- 全画面を日本語にする。
- 開発者以外にも操作できる言葉を使う。
- 社員番号と、内部のデータ識別番号を混同させない。
- 文字と背景のコントラストを確保する。
- 土日、選択日、主要操作、警告、承認状態を見分けやすくする。
- 色だけに頼らず、文字でも状態を示す。
- パスワードの表示・非表示切り替えを設ける。
- ログアウトボタンを分かりやすくする。
- 閲覧のみ・編集中・接続中・オフライン・提出待ちを明示する。
- 「保存」「提出」「取り込み」「承認」「確定」を区別する。
- エラー時は、利用者が次に何を確認すればよいか表示する。

# 18. 導入・更新・バックアップ

初回導入ツールを提供してください。

- 空の専用共有フォルダーを初期化する。
- 管理者グループのSIDを指定できる。
- 担当者のWindows SIDと社員番号を登録できる。
- 必要に応じて共有接続側のSIDも指定できる。
- 空でない業務フォルダーを誤って初期化しない。
- ファイル・フォルダーのアクセス権と、共有設定側のアクセス権の違いを説明する。

更新時は、既存データを保持したままスキーマを移行できるようにしてください。
旧版との混在が危険な場合は、バージョンの互換性確認と明確な更新手順を用意してください。

バックアップは次の両方を考慮してください。

- アプリから出力する業務データ
- 鍵・アカウント対応・未取り込み提出を含む共有フォルダー全体

復旧時のアプリ停止、整合する時点の復元、PC内の送信待ちの扱いも説明してください。

# 19. 必須テスト

少なくとも次を、自動テストまたは具体的な実機確認手順で検証してください。

- 初期管理者登録、ログイン、権限制御
- 担当者申請と承認
- 他人としての提出や自己承認の拒否
- 本人以外の情報が担当者データに含まれないこと
- 同月の編集排他、別月の並行編集、共通設定の排他
- 古い画面からの上書き防止
- ネットワーク切断と復旧
- 提出の再送・重複取り込み防止
- 編集中の月への取り込み保留
- 保存途中の失敗と復旧
- 日曜始まりの日付配置
- 日付別の勤務帯・時間範囲の反映
- 前月末を含む勤務の並び順
- 休みを挟んだ並び順
- 矛盾する希望と未達表示
- 未承認条件や自由文だけでは生成が変わらないこと
- 承認済み休暇と勤務希望が競合する場合
- 手動修正後の未達再評価
- 週・月・連勤の制限
- 休憩配置と人数不足の検出
- Excel・CSV・JSONの出力と入力検証
- 既存データの移行
- 配布ZIPに個人データや秘密鍵が含まれないこと
- EXEで起動し、HTTPサーバーが立ち上がらないこと

ローカルのダミーフォルダーで確認した範囲と、実際の社内LAN・複数PCでしか確認できない範囲を分けて報告してください。
